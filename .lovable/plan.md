# FakturaXL-driven refunds: corrections are created there, discovered here

New model: corrections are no longer generated by the app. You issue them manually in FakturaXL, the app discovers them on Sync, links them to the original sale, downloads their PDF, and then offers the matching Stripe refund — never issuing money without an explicit click.

## The flow being built

```text
FV EDU/2/08/2026  €73.80 paid via Stripe
   └── manual correction in FakturaXL → corrected total €40.00
          ↓ admin clicks Sync in /admin/sales
       FK row created, linked to the FV, PDF stored
          ↓
       "Correction detected — €33.80 refundable"
       [ Refund €33.80 via Stripe ]   [ Mark as settled manually ]
```

- Sync pulls in **every** correction against a sale, including a correction to a correction, and stores the number FakturaXL assigned.
- The refundable amount comes from the cumulative corrected state (€73.80 → €40 → €30 leaves €10 outstanding after the first €33.80 refund), never from the original FV alone.
- Each correction carries a settlement state: **awaiting decision**, **refunded via Stripe**, or **settled manually** — shown in the sales list and the row drawer.
- "Mark as settled manually" is reversible: the correction keeps a **Refund via Stripe** button, and clicking it opens a confirmation dialog naming the invoice, the correction number and the exact amount before anything moves.
- A correction bringing the total to zero is a full refund and revokes course access once settled; partial corrections leave access intact.
- The reverse mismatch is surfaced too: money refunded directly in the Stripe dashboard with no correction in FakturaXL shows as **"Refunded in Stripe — correction missing"**.
- Development mode: PDFs are stored, no email goes to buyers.

## Numbering

FK numbers now come from FakturaXL's own numbering (`FK EDU/n/mm/yyyy`), so the app stops calling `next_invoice_number` for corrections and stores whatever number the document has. FV numbering stays exactly as it is today.

## Technical details

**Schema**
- `invoices`: `settlement_status` (`awaiting` / `stripe` / `manual`), `stripe_refund_id`, `corrected_total_amount` (the corrected gross the FK establishes), `refundable_amount`, `settled_at`, `settled_by`.
- Unique index on `fxl_document_id` so a repeated Sync can never insert a second FK row for the same FakturaXL document — idempotency is keyed on the document id, and refunds additionally on `stripe_refund_id`.
- Discovered FK rows are inserted with `doc_type='FK'`, `invoice_number` copied from FakturaXL, and `original_invoice_id` resolved through the linking field confirmed in step A.

**Discovery (`invoice-actions`)**
- `sync_fxl` (single row) and `fxl_sync_all` (date range) additionally list `typ_faktury=4` documents, read each one, link it, insert or update the local FK row, and download the PDF via `pdf_p.php` into the private `invoices` bucket. Existing rate/amount reconciliation is unchanged. Rate-limit spacing (1 req/s for PDF, 1 req/5 s for listing) is respected.
- Amount handling follows the step-B finding; the refundable figure is derived from the corrected total, so a difference-style document and a corrected-state document both resolve to the same money.

**Stripe refund (`refund-payment`, rewritten)**
- Input is a **correction row id**, not a free-typed amount. It re-derives the amount server-side from the corrected state, refuses if the correction is already settled or if `stripe_refund_id` is set, and issues `stripe.refunds.create` for that exact amount against the original payment intent.
- On success: `settlement_status='stripe'`, `stripe_refund_id` stored, purchase `refunded_amount` / `refunded_at` updated, access revoked only when the corrected total reaches zero.
- It no longer creates any FakturaXL document.

**`stripe-webhook` (`charge.refunded`)**
- Stops calling `createInvoice`. It records the refund against the invoice, matches it to an existing FK by amount when possible, and otherwise marks the sale "refunded in Stripe — correction missing".

**What depends on the code being removed** (so nothing breaks when we delete it)
- `src/pages/admin/Sales.tsx:356` — the current `refund-payment` invoke and its amount-only dialog.
- `supabase/functions/stripe-webhook/index.ts:294` — the `charge.refunded` → `createInvoice` FK path.
- `supabase/functions/_shared/invoice.ts` — the `docType: 'FK'` branch and its `next_invoice_number('FK')` call.
- `supabase/functions/_shared/fakturaxl.ts` — the whole correction branch (`typ_faktury=4`, `<korekta>`, before/after position blocks) becomes dead code.
- `supabase/config.toml:22` — the `refund-payment` entry stays, since the function is rewritten rather than deleted.
- The `FK` row in `invoice_counters` and the `next_invoice_number` FK branch stay in place but go unused; existing FK rows (`FK EDU/1/08/2026`) keep working.
